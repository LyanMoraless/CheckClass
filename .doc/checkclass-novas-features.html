Verificação Facial no Login Escopo fechado, implementação não iniciada

Facial obrigatória em todo login feito de dentro da rede da instituição. Depende da Frente 12 (concluída) para a detecção de "dentro da rede" — essa parte, GAP-10, já está pronta. Reverte conscientemente uma decisão de privacidade fechada em 2026-08-21 (o match facial deixa de ser resolvido localmente no Raspberry e passa a rodar no backend) — decisão do usuário, registrada, não um erro a corrigir.

  • Quem e onde: todo login de todo mundo, mas só dentro da rede. De fora, continua CPF + senha.
  • Onde roda o match: no backend — rejeitados borda/Raspberry da sala e WASM no navegador.
  • Falha bloqueia o login, sem exceção — webcam quebrada ou máquina sem câmera impedem o acesso, aceito explicitamente.
  • Break-glass auditado para o administrador técnico; modo degradado automático foi rejeitado (derrubaria o serviço como forma de burlar a facial).
  • Cadastro biométrico presencial na secretaria, com consentimento assinado no ato — autocadastro rejeitado.
  • Menor sem consentimento do responsável não acessa o sistema — consequência aceita explicitamente, inclusive no início do ano letivo.

Cadeia prevista: Product Definition → Business Analyst → Security → Solution Architect → Tech Decision → Database → Backend + Frontend → Testing → QA → Project Guardian.

App Mobile Retomado em 2026-09-11 — reimplementação nativa

Desenvolvimento retomado por decisão do usuário em 2026-09-11 (a condição de pausa — portal web pronto — já estava cumprida desde 2026-09-03). O mecanismo de "refletir" o portal web no mobile também foi decidido: reimplementação nativa das telas que faltam, não WebView. Stack já aprovada (React Native/Expo) não muda.

  • O que o mobile tem hoje (6 telas): login, presença/faltas, cronograma, check-in, resolução de pendências (professor), conta (só logout).

Área de Provas inteira continua fora do mobile por decisão de produto anterior (depende de conceitos de navegador para monitoramento) — isso não muda.

  • Adiado, não rejeitado: conteúdo "Atividades" (Escola); paginação/filtro de data no cronograma (sem evidência de volume real que justifique).

Frente 08 — Decisões de Tecnologia Pendentes

O núcleo da Segurança de Intrusão já está implementado (detecção, incidentes, câmeras, autorização de área). Os itens abaixo são os que dependem de uma decisão de tecnologia ainda não tomada — diferente da tela de Áreas/Blocos, que é só um CRUD faltando no frontend (ver documento de pendências).

Adiado Vídeo ao vivo das câmeras pelo navegador

Confirmado pelo usuário: a intenção de produto de RULE-SEC-03 é vídeo ao vivo, não snapshot estático — mas a implementação depende do relay RTSP→HLS/WebRTC entre câmera e navegador, que segue "apenas sinalizado, não escolhido". Hoje o sistema já sugere automaticamente qual câmera é relevante para um incidente; só falta o mecanismo de exibir o stream em si.

Tecnologia não decidida Contagem exata de entrada/saída (RULE-SEC-05)

Confirmado por código: o pipeline de segurança registra cada cruzamento/leitura individualmente (intrusion_incident_location_entry), mas não existe contador agregado de ocupação por sala. Há inclusive um tipo de evento CAMERA_COUNT no pipeline de presença que é ingerido e imediatamente descartado. Direção técnica mais concreta já dada pelo usuário — câmera de sala de aula + visão computacional (ex. OpenCV), cruzada com contagem de tags via leitor de área, para auditoria/validação cruzada — mas a tecnologia final cabe ao Tech Decision + Computer Vision Agent, não decidida.

Gaps que vêm junto, nenhum perguntado: frequência exata da contagem periódica; o que acontece quando a contagem por câmera diverge da contagem por tag (incidente? alerta? só log?); se o mecanismo é exclusivo de sala de aula ou também se aplica a áreas gerais de segurança; se é a mesma câmera já aprovada para Segurança de Intrusão ou uma adicional.

Adiado Bloqueio automático de portas/ambientes (RULE-SEC-04)

Adiado desde 2026-08-23, não rejeitado. Ressalva inegociável já registrada: nunca prender pessoas durante uma emergência (incêndio, evacuação). Não há hoje, neste projeto, nenhum hardware relacionado a bloqueio de porta.

Limitação conhecida Horário semanal recorrente para permissão de área

wristband_category_area_permission.valid_from/valid_until modelam uma janela absoluta (um intervalo entre dois instantes), não recorrência do tipo "terças, 18h–22h". Nunca foi confirmado pelo usuário se isso é suficiente — não presumir que é defeito, nem que é aceitável. Levantar como pergunta objetiva quando esta frente voltar a ser tocada.
